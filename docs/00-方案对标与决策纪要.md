## 一、本项目的约束前提（与两份案例的根本差异）

| 维度 | 案例1（Gitee 小莫） | 案例2（iPaiKe） | **本项目** |
|---|---|---|---|
| 形态 | B/S Web 系统 | B/S + 移动端 + 企业微信 | **单机桌面软件，双击即用** |
| 部署 | MySQL + Node 服务 | Docker Compose，7 个端口，PostgreSQL+Redis+RabbitMQ | **零依赖，免安装，内嵌数据库** |
| 目标 | 落地教务系统 | 生产级开源产品 | **成果比赛演示：3–5 分钟讲清价值** |
| 首要指标 | 功能完整 | 工程完备 | **演示成功率 + 界面观感 + 算法亮点** |

> **关键推论**：案例2 的架构（消息队列、分布式锁、微服务化、K8s）在单机场景下全部是**负资产** —— 演示现场断网/端口冲突/容器启动失败都是致命事故。但它的**领域模型与规则体系**是全网能找到的最完整的一份，必须全盘吸收。

### 2.2 明确丢弃（单机场景下的负资产）

| 丢弃项 | 理由 |
|---|---|
| PostgreSQL / MySQL / Redis / RabbitMQ / Docker / K8s / Nginx | 单机软件用内嵌 SQLite，排课任务在本地工作线程跑，进度用事件回调 |
| JWT / Spring Security / 多角色权限体系 | 单机单用户，登录页若要保留仅作演示装饰（建议**省略**，直接进主界面，省 10 秒演示时间） |
| 移动端 / 企业微信集成 / 二维码 | 与单机定位冲突；如需"多端"亮点，用**导出图片/PDF + 本地二维码离线分享包**替代 |
| 学生管理 | 排课本身不需要学生个体数据（除非做高中走班选课）。**默认砍掉**，走班扩展时再以"选课组合"形式回归 |
| 数据同步中心 / Prometheus / Actuator / 审计日志 | 演示无价值 |
| 遗传算法（GA） | 参数多、收敛慢、演示时不可控。**改用模拟退火**：单参数（温度）易讲解，收敛曲线平滑漂亮，可随时中断取当前最优解 |

### 2.3 本项目独有、两份案例都没有的「比赛加分项」

> 这部分是拿奖的关键，评委看的不是 CRUD，是**你怎么把 NP 难问题讲成一个故事**。

| 亮点 | 说明 |
|---|---|
| **排课过程可视化** | 排课时实时显示：已填课时数进度、硬冲突数下降曲线、软约束评分收敛曲线、当前温度。让"算法在工作"这件事**看得见** |
| **前后对比看板** | 内置一份"人工排课"基线课表 vs 系统生成课表，并排展示评分差异（教师日负荷方差、学科分散度、主课上午占比、空隙课数）。用数据证明价值 |
| **课表体检报告** | 排完自动生成一页式诊断：哪几位老师负荷过重、哪个班下午连排三节主课、哪些规则被牺牲了及原因。**可解释性 = 评委最关心的点** |
| **一键载入示例学校** | 内置一所完整的示范初中（3 年级 × 12 班 × 45 教师 × 完整教学任务），零录入直接演示。同时提供"清空重来"，防止现场翻车 |
| **无解诊断** | 当资源不足无解时，不是报错，而是给出"缺 2 名数学老师 / 建议放宽体育课不排上午的限制"这类可执行建议 |
| **精美视觉** | 深浅色主题、学科配色体系、课表卡片化、拖拽带物理惯性与吸附反馈、排课完成的动效庆祝 |

## 三、待你确认的 6 项决策

> 以下每项都给出**推荐值**与理由。你只需回复"全部同意"或指出要改的编号。

### D1. 技术栈
**推荐：Electron + React + TypeScript + SQLite(better-sqlite3) + Tailwind CSS + shadcn/ui**

- 界面上限最高，课表网格、拖拽、动效、主题切换都有成熟生态
- `better-sqlite3` 同步 API，单机场景下比任何 ORM 都简单直接
- 打包 `.exe` 免安装绿色版，U 盘拷贝即可演示
- 排课引擎用 TypeScript 写在 Node 主进程 / Worker 线程，不阻塞 UI
- *备选*：若你更熟 Python，可换 PySide6 + SQLite，但界面精美度要多花 30% 工作量

### D2. 学段与规模（**已按反馈修订 v0.2**）

**推荐：三学段全覆盖、年级班级全动态、单年级 ≥ 20 班**

| 项 | 设计 |
|---|---|
| 学段 | `小学 / 初中 / 高中` 三学段并存，同一套数据库、同一个引擎；学段是**数据**不是分支代码 |
| 年级 | **完全动态**：不硬编码"一年级~六年级"。年级 = {所属学段, 名称, 入学年份, 排序号}，可增删改、可跨学段共存（九年一贯制 / 完全中学 / 十二年一贯制） |
| 班级 | 每年级**支持 ≥ 20 个班**（设计上限 40，无硬编码限制），支持随时增删班级并**局部重排**而非全量重排 |
| 规模上限 | 12 年级 × 20 班 = **240 个教学班**，约 600 名教师、10000+ 课时。这是设计容量目标 |
| 动态调整 | 学期中新增/合并/拆分班级、教师调岗、教室检修 → 触发**增量重排**：锁定未受影响的课表，只对受影响子集重新求解 |

**学段差异化通过"配置"而非"代码"实现：**

| 差异点 | 小学 | 初中 | 高中 |
|---|---|---|---|
| 作息模板 | 上午4 + 下午3 | 上午4 + 下午4 | 上午5 + 下午4 + 晚自习3 |
| 周上课天数 | 5 | 5 | 5 或 6 |
| 学科集合 | 语数英+道法科学音体美信息劳动 | +物理化学生物地理历史 | +技术、通用技术、校本 |
| 排课粒度 | 行政班 | 行政班（部分体育/选修合班） | 行政班 + **走班教学班** |
| 特色规则 | 晨读/午休/课后服务时段 | 连堂实验课 | 3+1+2 选科组合、大走班、分层教学 |
| 教师模式 | 包班/多科 | 一师多班单科 | 一师多班 + 跨年级 |

> 这些全部落在 `stage_profile`（学段配置）表里，新增一个学段 = 新增一行配置，**零代码改动**。演示时现场"切换到高中学段"并立刻重排，是很有冲击力的一幕。

**演示数据策略**：内置三套示例学校（示范小学 6×20 班 / 示范初中 3×20 班 / 示范高中 3×20 班 含走班），可一键切换。主演示用初中（60 班，秒级出结果），压力演示用全量 240 班展示性能。

### D3. 算法方案（**已按反馈修订 v0.2**）

**推荐：不做"一个算法"，做「可插拔多算法求解框架 + 算法对比实验台」。**

这是本项目**最大的评审加分点**：评委看到的不是"我用了模拟退火"，而是"我建了一个求解器平台，实现了 6 种算法，并用实验数据证明了在中小学排课场景下哪种最优"。这直接把项目从「软件开发」抬到「算法研究 + 工程实现」的层级。

完整算法菜单、原理、优劣与实现工作量评估见 **[`docs/07-排课算法选型菜单.md`](./07-排课算法选型菜单.md)**。

**分层落地策略：**

| 层 | 算法 | 定位 |
|---|---|---|
| **第 0 层：预处理** | 规则自检（约束传播 AC-3）、资源充分性校验、二分图匹配可行性判定（Hall 定理） | 提前暴露无解，给出可执行修复建议 |
| **第 1 层：构造** | ① 图着色贪心（DSATUR 启发式）<br>② CSP 回溯（MRV + 度启发式 + LCV + 前向检查） | 快速产出满足硬约束的可行解 |
| **第 2 层：优化**（可插拔，核心卖点） | ③ 模拟退火 SA<br>④ 禁忌搜索 TS<br>⑤ 遗传/模因算法 GA/MA<br>⑥ 自适应大邻域搜索 ALNS<br>⑦ 迟到接受爬山 LAHC | 同一接口、同一评分函数，**可在 UI 里自由切换与对比** |
| **第 3 层：算子** | Kempe 链交换、最小代价交换、块移动、教师—时段匈牙利重匹配 | 各优化算法共享的邻域动作库 |
| **第 4 层：修复** | min-conflicts 增量修复、局部重排 | 手工调课与动态调整时使用 |

**默认出厂配置**：DSATUR 贪心构造 → ALNS 主优化（自适应算子选择，收敛快且鲁棒）→ LAHC 精修。
**演示模式**：可切成"算法竞速"——多种算法并行跑同一份数据，实时绘制各自的评分收敛曲线赛跑，最后出对比报告。

### D4. 规则表达法
**推荐：采用案例2 的四层时段规则值 `FORBIDDEN / AVOID / NORMAL / PREFERRED`，作为统一的规则原语**

- 教师不排课、体育不上第一节、主课优先上午……全部可用同一套"时段偏好矩阵"表达
- UI 上就是一个可点击的「星期 × 节次」调色网格，直观且好看

### D5. 权限与登录
**推荐：无登录、无角色，直接进主界面。**（单机单用户，登录页只会浪费演示时间）
- 若比赛评分表明确要求"权限管理"，则加一个极简的"管理员/查看者"开关
