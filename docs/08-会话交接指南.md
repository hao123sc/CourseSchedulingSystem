# 08 · 会话交接指南

> 用途：本项目需跨多个 AI 会话完成开发。新会话的助手**没有任何历史记忆**，本指南规定如何在几十秒内恢复上下文、如何工作、如何收尾。

---

## 1. 核心机制：三个文件构成记忆

| 文件 | 作用 |
|---|---|
| **`PROGRESS.md`** | **唯一事实来源**。当前进度、已锁定决策、纪律、风险、变更日志 |
| `docs/06-开发计划.md` | 里程碑 M0~M9 的任务清单与验收标准 |
| `docs/0X-*.md` | 各领域详细设计，实现时按需查阅 |

**铁律**：任何会话开始先读 `PROGRESS.md`，结束前必须更新它。它不更新，下个会话就"失忆"。

---

## 2. 每个会话的标准流程

```
┌─ 开场（助手自动执行）──────────────────────┐
│ 1. 读 PROGRESS.md → 知道做到哪、什么不能改  │
│ 2. 读 docs/06 对应里程碑 → 知道这次做什么   │
│ 3. git log --oneline -10 → 看最近做了什么   │
│ 4. 复述一遍计划，等你确认                   │
└────────────────────────────────────────────┘
                  ↓
┌─ 执行 ─────────────────────────────────────┐
│ · 按里程碑任务清单逐项实现                  │
│ · 每个逻辑单元独立提交                      │
│ · 遇到与已锁定决策冲突 → 先问，不擅自改      │
│ · 遇到文档未覆盖的设计空白 → 先问，不擅自定  │
└────────────────────────────────────────────┘
                  ↓
┌─ 收尾（助手自动执行）──────────────────────┐
│ 1. 跑验收项自检，逐条报告结果               │
│ 2. 清理临时文件，git status + du -sh 验证   │
│ 3. 更新 PROGRESS.md（进度/日志/新增风险）   │
│ 4. 提交推送                                 │
│ 5. 输出「下次从这里继续」的交接说明          │
└────────────────────────────────────────────┘
```

## 3. 提示词模板（复制即用）

### 3.1 开启新会话 · 通用启动词（**最常用，每次粘这个**）

```
这是一个跨会话的项目。请先执行以下步骤再动手：

1. 读 PROGRESS.md，了解当前进度、已锁定的决策、工作区纪律
2. 读 docs/08-会话交接指南.md
3. 读 docs/06-开发计划.md 中「下一个里程碑」对应的章节
4. git log --oneline -10 看最近提交

然后用不超过 10 行复述：这次要做什么、验收标准是什么、有哪些注意事项。
等我确认后再开始写代码。

约束：
- 只在 arena/01a0e81b-courseschedulingsystem 分支工作
- 不得推翻 PROGRESS.md 中已锁定的决策（D1~D8），如认为需要改动先问我
- 遵守工作区纪律：不产生临时文件，node_modules 不入库，每步后清理
- 遇到文档没覆盖的设计空白，先问我，不要自己定
```

### 3.2 执行指定里程碑

```
按 docs/06-开发计划.md 执行 M3（排课引擎 v1）。

要求：
- 先列出本里程碑的任务清单与你的实现顺序，等我确认
- 详细设计查 docs/04-排课算法设计.md，数据结构查 docs/03
- 每完成一个逻辑单元就提交一次
- 结束时逐条报告验收项达成情况
```

### 3.3 里程碑太大需要拆分时

```
M5 内容较多，本次会话只做前半部分：
评分器 + 增量评分缓存 + Move 接口与算子库（swap/move/kempe）。
ALNS 与 LAHC 留到下次。

完成后在 PROGRESS.md 里把 M5 标为「🟡进行中」并写明已完成/未完成的具体条目。
```

### 3.4 UI 实现时

```
按 docs/mockups/timetable.html 实现课表页。

- 视觉稿是定稿，配色、间距、圆角、动效参数直接照搬
- 设计 token 见 docs/05-界面与交互设计.md 第 2 章
- 用 React + Tailwind + shadcn/ui 重写，不要直接内嵌那个 HTML
- 完成后截图或启动 dev server 让我看效果
```

### 3.5 接手上个会话未完成的工作

```
上个会话 M4 做到一半。请：
1. 读 PROGRESS.md 看未完成条目
2. git log --oneline -5 和 git diff HEAD~3 --stat 看已做了什么
3. 列出剩余任务，等我确认后继续
不要重做已完成的部分。
```

### 3.6 只做排障，不推进

```
不要推进新功能。当前问题：<描述现象>

请先定位原因再改代码，改动范围控制到最小，并说明为什么这样改。
```

### 3.7 会话结束前（如果助手忘了收尾）

```
收尾：
1. 逐条报告本里程碑验收项的达成情况
2. 清理临时文件，跑 git status 和 du -sh 验证
3. 更新 PROGRESS.md：进度表、变更日志、新发现的风险或易错点
4. 提交推送
5. 给出下次会话的第一条指令
```

## 5. 什么情况必须停下来问你

助手在以下情况**不得自作主张**，必须先征询：

1. 需要改动 `PROGRESS.md` 中 D1~D8 已锁定的决策
2. 需要引入文档未提及的新依赖（尤其是原生模块、大体积库）
3. 发现设计文档之间有矛盾
4. 某个验收指标达不到，需要降低标准
5. 里程碑工作量明显超出单次会话，需要拆分
6. 需要删除或大幅重写已有代码

---

## 6. 上下文预算管理

单次会话上下文有限，避免浪费：

| 做法 | 说明 |
|---|---|
| **不要一次读完所有文档** | 只读 `PROGRESS.md` + 当前里程碑相关的 1~2 份文档 |
| **一个会话只做一个里程碑** | 做完就收尾，不要贪多导致后半程质量下降 |
| **大里程碑主动拆分** | M1、M5 内容多，建议拆成两次会话 |
| **不要重复粘贴文档内容** | 文档在仓库里，让助手自己读，不要贴到对话里 |
| **代码审查用 diff** | 让助手报告 `git diff --stat` 而非贴全文 |

## 7. 质量守门

每个里程碑结束时，助手必须逐条回答：

```
验收自检
─────────────────────────
□ AC-x  <验收项>        结果：通过 / 未通过（原因）
□ ...
工作区
─────────────────────────
git status              干净 / 有残留
仓库体积                XXX KB
新增依赖                无 / <列表>
遗留问题
─────────────────────────
<如有>
```

特别地，**M3 之后每次涉及引擎的改动都必须跑基准**：

```
npm run bench
```

并对比 `docs/06-开发计划.md` M5 验收项中的回归指标阈值。

## 8. 如果会话中断或出问题

| 情况 | 处理 |
|---|---|
| 会话意外中断 | 新会话用 3.5 的提示词接手，先看 git log 确认落盘到哪一步 |
| 助手改坏了代码 | `git log --oneline` 找到好的提交，`git revert <sha>`（不要 reset --hard 丢历史） |
| 助手推翻了已定决策 | 指出 `PROGRESS.md` 中对应的 D 编号，要求回退 |
| 不确定做到哪了 | 让助手跑 `git log --oneline -20` + 读 `PROGRESS.md` 后复述 |
| 仓库变大了 | `du -sh .git`、`git count-objects -vH`，检查是否误提交了 node_modules 或 db 文件 |
